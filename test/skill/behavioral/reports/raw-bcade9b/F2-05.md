## Debate: caching strategy

**Position A — Cache hard.** Put a cache in front of reads by default. Most traffic hits the same small data set, so a cache turns a 200 ms database call into a 5 ms hit. Short staleness (30–60 s) is a fair price on most product surfaces.

**Position B — Cache carefully.** A cache is a copy you promise to keep fresh. The hard part is not the hit; it is the stale read after a write. Invalidation bugs are silent: old prices, old permissions, old state. Add a key only when you can name its invalidation event.

### Round 1 — Openings

- **A:** Start with a long TTL and a simple purge path. You get speed now and tighten later. The 90% of reads that are near-static (config, reference data, product pages) should not wait on a full invalidation design.
- **B:** "Tighten later" never happens — the stale-read bug report arrives first. A permission cached for 60 seconds is a security event, not a trade-off. A long TTL also hides write-path bugs: the system looks fast while it serves wrong answers.

### Round 2 — Rebuttals

- **A vs B:** Versioned keys and short TTLs bound the damage without a big design. Perfect invalidation up front blocks shipping and pushes teams to skip caching entirely — then the database falls over under read load.
- **B vs A:** A per-feature "we will add invalidation later" note is not a design. If you cannot say which event drops the key, you do not own the data — you rent it and hope. And a wrong answer served fast is worse than a slow right one.

### Round 3 — Concessions

- **A concedes:** Tiering by cost of staleness is right. Auth, permissions, and money get no cache, or write-through with near-zero TTL.
- **B concedes:** Refusing all caches until invalidation is perfect is too slow. A small per-key policy — TTL plus one named invalidation event — is enough, and you can do it per feature.

---

## Summary

- The real split is not "cache vs. no cache" — it is **per-key staleness cost**.
- Rule: name the invalidation event before you add the key. If you cannot, cap the TTL to the worst stale window you can defend.
- Never cache auth, permissions, or money without write-through or a near-zero TTL.
- Watch hit rate and stale-read reports together; speed on wrong data is a regression.

## Debate: caching strategy

**Topic:** caching for a read-heavy web service.
**Position A:** cache aggressively, at every layer.
**Position B:** cache conservatively, only with proof of need.

### Round 1 — opening claims

**A:** Put a cache at every layer: browser, CDN, application memory. Most reads then never reach the database. Latency drops, and the database stays small. Short TTLs bound the staleness, so the risk stays small too.

**B:** Every cache adds two problems: stale data and invalidation. Cache only data that is expensive to compute and rarely changes. Start with no cache. Add one when measurements show a real need. A cache is an optimization, not a default.

### Round 2 — rebuttal

**A against B:** "No cache until measurements show a need" fails at the first traffic peak. The database falls over before you can add a cache. A cold system under load is an incident, not a baseline. Aggressive caching with short TTLs is cheaper than that outage.

**B against A:** Aggressive caching moves complexity into the cache layer. After a write, users see old values, and nobody knows which layer holds them. Invalidation across many layers is the classic hard problem. You trade a slow system for a system that is sometimes wrong and always hard to debug.

### Round 3 — concession and boundary

**A concedes:** For data where a wrong value costs money or safety — balances, permissions, stock levels — B is right. There, cache nothing, or use write-through with explicit invalidation.

**B concedes:** For static or near-static data — product pages, config, reference data — A is right. Aggressive caching with short TTLs is the correct default there, and "measure first" only wastes time.

---

## Summary

The positions do not truly conflict. They differ on the **default** and on **risk appetite**.

Decision rule — classify each data set by three questions:

1. What does staleness cost?
2. What does recompute cost?
3. Do reads dominate writes?

| Data class | Strategy |
|---|---|
| Staleness cheap, reads dominate | Cache aggressively, short TTL |
| Staleness costly | No cache, or write-through with explicit invalidation |
| Expensive to compute, rarely changes | Cache with explicit invalidation |

Practical close: start with few caches, one invalidation path per data class, and add layers only when measurements demand them.

Positions: **A — cache-first** (cache early, invalidate exactly) vs **B — measure-first** (cache late, bound staleness with TTL).

### Round 1 — Opening case

**A:** A cache hit is 10–100× cheaper than a database read or a recompute. Read traffic follows a power law: a small set of keys covers most requests. So cache the hot paths from the start, and invalidate on write.

**B:** Every cache is a second copy of the truth. Invalidation is where most bugs come from: a missed purge serves wrong data with no error. Start with no cache, watch the metrics, and add a cache only where misses cost real time. Use TTL to bound staleness.

### Round 2 — Rebuttal

**A:** A TTL is a guess. Between writes, users see stale data — that is a correctness bug, not a trade-off. If you own the write path, event-driven invalidation is exact and cheap. "Measure first" moves the cost to incident response.

**B:** Event-driven invalidation couples every writer to every reader's cache keys. One wrong key, and you serve stale data forever — silently. A 30-second TTL bounds the same mistake to 30 seconds. Fan-out on purge is also its own failure mode.

### Round 3 — Closing

**A:** For shared, read-mostly data — reference tables, derived views, config — cache hard and invalidate exactly. I concede: per-user data with low reuse, write-heavy sets, and cold paths do not belong in a long-lived cache.

**B:** For fast-changing, correctness-critical data — balances, inventory, permissions — use a short TTL or no cache. I concede: static and slow data should be cached hard, with a long TTL or an explicit purge.

### Summary

- The real question: (reuse rate × cost of a miss) vs. cost of staleness.
- Cache hard: static reference data, derived read models, hot keys where you own the write path.
- Cache soft or not at all: per-user, fast-changing, correctness-critical data.
- Mechanism: explicit invalidation when you control writes; TTL when you do not.
- Both sides agree: a cache without hit-rate and staleness metrics is a liability. Add metrics with the cache, not after.
